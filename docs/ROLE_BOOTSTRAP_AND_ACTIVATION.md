# Role Bootstrap and Activation

Core alone recognizes and activates a separate owner/role. Lifecycle states are `proposed`, `recognized_inactive`, `owner_adoption_required`, `active`, and `superseded`; only `active` is dispatch-authorized. A generated scaffold or example is non-authorizing regardless of how complete it appears.

Start with a demonstrated boundary and user/Core recognition. Establish a stable owner ID distinct from the Git owner; assign branch namespace and worktree-root prefix; state authority and explicit non-ownership; then map owned files, decisions, and capabilities. Record upstream public contracts and downstream consumers, never another owner's private implementation. Use A2A escalation for missing contracts or disputed boundaries.

Create role instructions, bootstrap prompt, continuity MOC/protocol/receipt/transcript roots, an orchestration profile with exact lane bindings and checks, vault scope/parentage, feature/package documentation, tests, and conformance witnesses. The proposed owner authors an adoption record; Core validates dependency evidence, integrates the approved changes, changes lifecycle state to active, and assigns the first bounded task. Retirement changes state to superseded while preserving continuity and provenance.

Activation evidence must identify the boundary decision, user/Core recognition, adopted profile, verification, canonical/registry synchronization, and integration disposition. No automatic generator is provided because these are authority-bearing decisions rather than safe boilerplate.
