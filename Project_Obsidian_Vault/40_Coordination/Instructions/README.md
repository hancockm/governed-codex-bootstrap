This hub routes active owners and supporting review roles to shared
coordination rules. Root [AGENTS.md](../../../AGENTS.md) remains the repository-wide operational
authority. These notes explain how those rules apply inside the vault without
creating a second, divergent policy source.

## Required Starting Order

1. Read root [AGENTS.md](../../../AGENTS.md).
2. Read the active owner's role, bootstrap prompt, continuity MOC, and profile.
3. Read [[40_Coordination/Instructions/All Owners User Collaboration And Decision Semantics]].
4. Read [[40_Coordination/Instructions/Universal Work Selection Audit]] for
   substantial next-step selection.
5. Read the active coordination index and only records relevant to the task.
6. Verify every material repository claim against current evidence.

Inactive templates are examples, not dispatch authority.

## Critique Preamble And Shape

Begin a substantive critique record with this project-neutral preamble:

```text
Be critical of this input. Analyze it as a proposal, not as the answer. Identify common agreement, list all remaining disagreements, expose weak assumptions, and make one convergence move. A useful iteration reduces disagreement rather than continually inventing new categories.
```

Then use these headings in order:

1. Common Agreement
2. All Remaining Disagreements
3. Critical Weak Points
4. Convergence Move
5. Decision Status

The owning agent records each substantive point as `Accepted`, `Partially
accepted`, `Rejected`, `Deferred`, or `Requires user approval`. Strong review
language does not create authority.

## Binding Coordination Rules

- Exploratory material and critique are context, not implementation approval.
- Ownership is strict; another owner's work requires a boundary request.
- Coordination records are source material, not canonical doctrine.
- External critique completes only when the assigned record contains valid
  output; process exit or empty stdout is insufficient.
- Cross-owner requests and responses must be reachable from the recipient's
  shared canonical Git history.
- Generated records and indexes are tool-owned and must not be hand-edited.
- Cross-owner transcript duplication is prohibited; link to the owning pack.
- Root Git and worktree policy is not copied into role instructions.

## Planning Routine

Before finalizing a substantial plan:

1. freeze the first inspected baseline;
2. identify one candidate and its owner;
3. inspect relevant canonical, capability, source, test, configuration, and
   Git evidence;
4. inspect relevant A2A requests and dispositions;
5. create the source-only work-selection audit;
6. create a plan critique handoff when required;
7. disposition every substantive critique point;
8. identify all owner-dependent questions;
9. record which canonical documents require synchronization or why none do;
10. present the bounded plan for user approval.

Unrelated repository churn is a delivery condition, not a reason to restart
selection analysis.

## Implementation And Publication

After approval, the implementation cycle includes code or documentation,
focused and broad verification, canonical/package synchronization, capability
evidence, A2A completion records, generated navigation, scoped Git delivery,
branch reconciliation, and continuity closeout.

An A2A record required by another owner must not remain trapped on an unlanded
feature branch. Publish it through the authorized integration lane and verify
reachability before describing the recipient as blocked.

## Role Model

- Core is the only initially active owner and primary-branch integrator.
- Future feature owners are created only through the activation protocol.
- Review and external-critique agents are supporting roles, not implementation
  owners.
- Implementer and verification lanes inherit the active owner's authority and
  cannot expand it.

## Context Compression

Read MOCs and active indexes first. Do not load every transcript, archive, or
historical record by default. Atomic records live beneath generated indexes;
top-level files remain compact and navigable.

## Feature Documentation Routine

Before feature work, read the public Core contract pattern, source
documentation style, feature documentation standard, matching package README,
feature vault MOC, active owner instructions, and relevant boundary requests.
If those assets do not exist, remain inactive and route owner initialization
through Core.
