This area contains owner-scoped feature concepts and documentation. A feature
does not exist as an active owner merely because a folder or template exists.

## Before Activation

Keep proposals visibly inactive. Record the demonstrated boundary, public
Core contracts required, decisions the future owner would own, explicit non-
ownership, evidence sources, and expected consumers. Do not create fictional
domain truth or copy an unrelated mature feature manual.

## Activation

Core follows [docs/ROLE_BOOTSTRAP_AND_ACTIVATION.md](../../docs/ROLE_BOOTSTRAP_AND_ACTIVATION.md): recognize the boundary,
create inactive connected assets, obtain owner adoption, validate dependency
architecture, integrate, and publish an activation commit. Only then may the
owner dispatch work.

## Feature Documentation

An active feature maintains purpose, maturity, owned and prohibited paths,
public contracts, module/folder map, canonical imports, tests, vault MOC,
role instructions, bootstrap prompt, continuity pack, and retirement evidence.
Follow [docs/FEATURE_AGENT_DOCUMENTATION_STANDARD.md](../../docs/FEATURE_AGENT_DOCUMENTATION_STANDARD.md).

## Cross-Owner Changes

Feature owners consume public contracts. Missing Core or other-owner behavior
travels through a durable A2A request rather than a feature-local substitute.
Stable conclusions that change project-wide doctrine return to Core for
canonical disposition.
