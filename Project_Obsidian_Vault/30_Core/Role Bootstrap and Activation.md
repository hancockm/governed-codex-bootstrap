Core uses [docs/ROLE_BOOTSTRAP_AND_ACTIVATION.md](../../docs/ROLE_BOOTSTRAP_AND_ACTIVATION.md) as the maintained
role-creation protocol. Only an `active` registered owner is dispatch-
authorized; a scaffold remains non-authorizing until adoption, evidence,
integration, and Core activation are complete.

Map stable/Git identity, branch/worktree namespace, authority/non-ownership,
owned paths/decisions/capabilities, the owner Core Thesis, Architecture, Spec,
and Implementation Roadmap, public upstream contracts, downstream consumers,
continuity roots, orchestration binding, vault parentage, feature docs, tests,
and retirement provenance.

## Activation Summary

```text
demonstrated boundary
→ Core recognition
→ inactive four-document canon, dependency profile, and connected assets
→ proposed owner review and adoption
→ conformance and integration
→ Core activation commit
→ first bounded owner task
```

`proposed`, `recognized_inactive`, and `owner_adoption_required` do not grant
dispatch authority. `active` is the only operational state. `superseded`
removes authority while retaining provenance, continuity, and ownership-
transfer evidence.

The profile must expose public upstream contracts and downstream consumers.
Private implementation dependencies across owners fail closed. Shared Git,
continuity, and orchestration policy is referenced from root instructions, not
copied into the new role.

The owner-local Core Thesis explains why the owner exists; Architecture defines
its components and boundaries; Spec defines observable contracts; and the
Implementation Roadmap orders accepted capability gates. Missing or unadopted
documents block activation. They govern only the owner scope and cannot
override project-wide canon.
